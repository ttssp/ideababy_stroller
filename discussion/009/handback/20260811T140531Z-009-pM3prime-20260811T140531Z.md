## §2 逐条整改详情

### 2-1 R1 · source_ids 全局顺序强制等于 ORDER BY id 权威序列

**背景(评审 C 原话)**:「同 source 内错配今天已无任何检测器」,比 build 自述的「仍不能证明」更差 ——
四道既有关(等长 / 身份键 / 清单锚 / 乱序检测)逐条失明,暴露面 **35/41(85%)** 落在多信号桶内(真盘
41 条信号 / 14 distinct source)。今天不是坏的(worksheet 行首整数序列实证 == `ORDER BY id` 序),
但没有任何代码强制这个前提,属 **latent**。

**修法**:`blind_annotate.py` 新增 `_assert_source_ids_match_canonical_order(conn, caliber_version,
source_ids)`,查 `SELECT source_id FROM extracted_signals WHERE caliber_version=? ORDER BY id`,
要求与传入 `source_ids` **逐位相等**(不止 `Counter` 多重集)。调用点放在 `reconcile()` 内既有多重集 /
身份检查**之后**(不改变那些检查自身的诊断信息;到这一步还没被挡下的,才是"多重集对、身份对,但全局
顺序漂移"这一类专属于 R1 的新增暴露面)。

**mutation-kill 测试**:`tests/contract/test_f3_machine_from_db.py::
test_should_reject_when_reconcile_source_ids_diverge_from_canonical_order` —— 把 s2 插到两条 s1
中间(多重集不变),证明此前会被四道关全部放行、现在必须拒绝。去掉守卫,该测试直接变红
(`DID NOT RAISE`,已实测确认)。

**已核对不误伤**:全仓仅 3 个测试文件调用 `reconcile()`,逐一核对其 `source_ids` 与插入顺序本就一致
(production 路径与既有测试的 `source_ids` 本就等于插入顺序),0 回归。

### 2-2 R2 · 语义问题回答 + 纯文档订正(不加绑定代码)

**评审 C 提出的语义问题**:`extracted_signals.created_at` 是普查时刻还是提取时刻?

**回答(先答后动手,与 IDS 要求一致)**:实测 `census.py::run_census` 的证据 ——

```python
now = conn.execute("SELECT strftime(...,'now')").fetchone()[0]   # 循环外,唯一一次
for sid in sampled_sids:
    ...
    conn.execute("INSERT INTO extracted_signals (...,created_at) VALUES (...,now)")
```

`now` 在进入逐条记录循环、发起任何 LLM 调用**之前**只取一次,该批**全部**信号(不论来自哪条记录)共享
同一个时间戳,条目间零区分度。全仓 grep 确认该列**从未被任何生产 SELECT 读取过**(只写不读)。

**结论:不可用作提取时点独立锚**。按 IDS 给定的条件句(「若不可用作提取时点锚,正解是在契约里明写
「时序关是自报的」,而不是加代码假装绑定」),本次**未新增任何绑定代码**,只在 `gold_layer2.py`
(`machine_extracted_at`/`blind_annotated_at` 入参注释 + `_blind_annotated_strictly_before_machine`
docstring)与 `blind_annotate.py`(`reconcile()` docstring + CLI `--machine-extracted-at`/`--annotated-at`
help 文案)明写:两个时间戳都是调用方自报字符串,系统当前**无法**独立核验"这条信号真的是在这个时刻被
提取的"。

无对应可 mutation-kill 的代码测试(没有代码分支被改动,纯文档)。

### 2-3 R3 · payload 形状 fail-closed

**背景**:`assert_machine_payload_matches_db` 此前只核对"携带的"字段 —— payload 整体是 dict、或每条
是空对象、或键名打大小写错(如 `Ticker` 而非 `ticker`),三种都因为"零字段被携带 → 全部跳过核对"而被
ACCEPTED。无数值后果(最终恒用 DB 值),但语义有害:一份形状不对的陈旧/打错字文件会拿到绿灯,
operator 会误读成"已被核验"。

**修法**:加两条前置校验(不改变"未携带字段跳过核对"的既有诚实边界)——① `payload` 必须是非字符串的
`Sequence`,否则 raise;② 每条元素必须是 `Mapping` 且至少携带一个可核对字段(含 `source_id`),否则
视为"形状不可核验"而 raise。

**测试**:`test_should_raise_when_machine_payload_is_a_dict_not_a_list` /
`test_should_raise_when_machine_payload_entries_are_empty_objects` /
`test_should_raise_when_machine_payload_uses_wrong_case_keys` —— 三条负例此前均 `DID NOT RAISE`
(已实测确认红 → 绿)。

### 2-4 R4 · 修正两处失真措辞 + 修正一条"绿但守错关"的测试

**`_assert_source_id_alignment`**:docstring 曾称"**三方**身份绑定校验"。F3 ③ 之后 `reconcile()` 里
的 `machine` 恒等于 `load_machine_from_db` 的返回值,而后者对每条记录的 `source_id` 就是从 DB 该行
原样取出、再放回原位置 —— `machine[i]["source_id"] == source_ids[i]` 对生产路径是**由构造保证的恒真式**,
不是本函数"验出来"的。已订正措辞:保留三者遍历(无害的防御性冗余),但明确说清真正在验证的只有
human 与 gold 两方。

**`_assert_matches_registered_sample_manifest`**:docstring 曾称"**三份 JSON** 的 ID 全部来自调用方"。
同理已订正:machine 自 F3 ③ 起不再是调用方提供的独立 JSON。

**`test_should_reject_when_machine_order_shuffled`**:该测试此前的 docstring 自称"逐位比对挡住了乱序",
但其 fixture DB 只有 `s1` 一行 —— 它实际是被 `load_machine_from_db` 的多重集校验(`s2` 根本不在 DB
清单里)挡下来的,不是它标题所说的"乱序检测"。已订正 docstring 如实说明,并新增
`test_should_reject_machine_payload_when_source_id_order_swapped`(在一个真含 `s1`+`s2` 两个 source
的独立 DB 上,验证 `assert_machine_payload_matches_db` 才是 F3 ③ 后真正守"machine 侧顺序对不对"这条关
的函数)。
