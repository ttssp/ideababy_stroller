## §1 Rationale(执行摘要)

P2 production end-to-end run (the M3 go/no-go gate number) is currently UNREACHABLE due to a missing 008-to-004 signal backfill chain, and closing it the obvious way would violate spec OUT-10. This hand-back surfaces the precondition gap for operator decision in IDS rather than guessing data or crossing the OUT-10 boundary in XenoDev.

CONTEXT: IDS handback-review 009 returned the M3 go/no-go decision to the operator, gated on whether M2 sample size is DSR-significant, i.e. on actually running decision_ledger.alpha.evaluate --advisor <real-id> against real data and reading real hit_rate/dsr/pbo/trial_count rows in analyst_alpha_eval. The operator asked to do a build-then-probe pass (no production credentials touched) to scope that run. This hand-back is the probe result.

WHAT evaluate READS (verified from alpha/join.py:105-140): for a given advisor_id it walks 004 tables advisor_reports (advisor_id, source_id, week_id, structured_json), joins strategy_signals (ticker/direction/created_at as the authoritative signal_published_at) and watchlist (ticker -> market authoritative lookup). It does NOT read any 008 collection store.

GAP 1 (the blocker) — no 008-to-004 signal backfill chain in this repo: the 008 collection pipeline produces a CONTENT store (collection.db: 图文/回放/问答 raw material for the trader-team corpus), NOT 004 advisor_reports / strategy_signals rows. In XenoDev projects/008-pB/ contains only probe docs + AGENTS.md + tech-stack.md; the real 008 collection system is separately deployed (systemd twin-daemon, its own DB) and there is NO implemented path that transforms 008 collected content into the 004 advisor_reports.structured_json / strategy_signals rows that evaluate consumes. Consequence: with empty 004 source tables, evaluate runs structurally but returns resolved_signals=0 / accepted_rows=0 (no crash, just no alpha number) — verified from evaluate.py:151-174. So the M3 gate number cannot be produced until this backfill chain exists.

GAP 2 (why the naive fix is out of bounds) — strategy_signals has no advisor-locator key: alpha/join.py:23-30 already documents (this was a T011 red-team #B finding the builder proactively branched to hand-back, not a new discovery): strategy_signals table has no advisor_id column and inputs_used has no advisor key; join scope is bound only via advisor_report.week_id (a calendar string carrying no advisor identity). Under the v0.1 single-advisor assumption (domain/advisor.py:28 — source_id is schema-reserved, v0.1 = advisor_id) this does not misfire. But a real multi-advisor production backfill would double-attribute the same strategy_signal row to two advisors (false accepted / false multi_direction). The thorough fix = add an advisor-locator key to 004 strategy_signals (touching advisor_strategy.py signal production + a data backfill), which (a) is outside the alpha/ file_domain T011/T012 were scoped to, and (b) CROSSES spec OUT-10 (do not change already-shipped 004 StrategyModule / PriceDataProvider contracts / signal-production schema). Crossing OUT-10 = BLOCK. So even wiring a backfill cannot be done cleanly in-scope; it needs a spec decision.

INFRASTRUCTURE STATE (probe, no credentials touched, nothing written): production data.sqlite does not exist anywhere (default DECISION_LEDGER_HOME/data.sqlite = ~/decision_ledger/data.sqlite, absent; full-tree scan found no non-test sqlite). Both alembic upgrade head and the evaluate CLI go through config.load_settings() which HARD-FAILS without ANTHROPIC_API_KEY (ConfigError: ANTHROPIC_API_KEY cannot be empty) — a credential-isolation boundary (three hard constraints, credentials never in agent context); the CLI --db flag exists precisely to bypass the unrelated-key settings validation. So DB creation itself needs the operator production .env. Per operator instruction the probe stopped before creating the DB (build-then-probe only).

WHY THIS IS A spec-gap NOT a XenoDev-internal fix: the missing 008-to-004 backfill chain is a cross-fork integration surface whose ownership was never assigned (009-pForge spec scoped M1 price layer + M2 alpha head consuming ALREADY-EXISTING 004 advisor signals; it assumed advisor_reports/strategy_signals are populated upstream, but in the current deployment they are not, and the populate path is not in any fork). Closing it touches either (a) a new ingestion/backfill component (whose fork/PRD does not exist) or (b) already-shipped 004 schema (OUT-10 BLOCK). Both are IDS-governance decisions (idea/PRD/forge SSOT), not XenoDev iterations. Recording rather than acting also avoids the V4 failure mode (silently guessing data or crossing a BLOCK line to force a number).

SUGGESTED IDS ACTIONS (operator decides): (1) decide who owns the 008-to-004 advisor-signal backfill chain — a new fork/PRD (e.g. a 008-to-004 bridge) or an explicit extension of an existing one; note it may need real advisor PDFs/reports as input, which is itself an upstream data-availability question. (2) decide the multi-advisor strategy_signals advisor-locator key: either keep the v0.1 single-advisor assumption explicit and defer the key (evaluate works for exactly one advisor as long as its advisor_reports/strategy_signals are populated), or authorize an OUT-10 amendment to add the locator key (a spec revision, since it changes shipped 004). (3) until a backfill exists, the fastest way to get ANY real M3-gate number is a scoped smoke path: manually insert a small set of REAL historical signals for ONE real advisor (real ticker/direction/date) into 004 advisor_reports + strategy_signals + watchlist, ingest the matching real prices (P1), then run evaluate — this exercises the full P2 chain end-to-end and yields real hit_rate/dsr/trial_count (or an honest insufficient_sample per O9), enough to inform M3 go/no-go WITHOUT building the general backfill or crossing OUT-10. This smoke path needs operator-supplied real values + production credentials (credentials never enter agent context; I can only provide the command skeleton + precondition checklist).
