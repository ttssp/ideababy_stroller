  走的是完全不同的证据路线(市场结果,不是人工标注)。

## 3. 冻结项 A · 提取范围

### 3.1 纳入(article + replay 全量)

```
form ∈ {article, replay}
AND capture_status = 'captured'
AND NOT is_in_oos_window(published_at)        # C12 冻结窗 [2025-12-01, 2026-02-01)
AND text 非空
```

预期规模:**≈1365 条记录 → ≈900 条信号**(其中 US 约占 98%,按 E1 实测 US 40 / CN 1 / HK 0)。

### 3.1b 🔒 冻结:方案 B(operator 2026-08-12 选定)

三个候选方案与实测代价(计时试验数据见 §6):

| 方案 | 记录数 | 预估墙钟(串行) | 外推信号 |
|---|---|---|---|
| A · article only | 1055 | ≈2.3 h | ≈790 |
| **B · article + replay** ✅ **选定** | **1364** | **≈3.8 h** | **≈905** |
| C · 全量含 qa | 7364 | ≈17 h | ≈1092 |

**选 B 的理由**:信号条数不是瓶颈(A 的 790 已是所需 158 的 5 倍),**有效样本才是** ——
现有 41 条的集中度是 61% 半导体 / 78% long / 仅 13 个不同时点。
`record_tickers` 表(777 条标注 · **252 个不同 ticker** · NVDA 仅占 6%)显示
**多样性集中在 replay**,而该表**只覆盖 replay**。多花 1.5 小时买多样性,直接改善有效样本。

### 3.1c ⚠ 执行绕法:CLI 表达不了本范围,用过滤输入实现

`census --sample-size` **对三个 form 一视同仁**(`build_sampling_plan` 里 `_FORMS` 硬编码为
`(article, qa, replay)`),因此**无法用 CLI 表达「article+replay 全量、qa 零条」**。

**采用的绕法(零代码改动)**:给 census 喂一份**过滤后的 collection 副本**,其中 qa 记录已删除:

```sql
-- 派生自 /home/ys/codes/XenoDev/out/collection.db
DELETE FROM records WHERE form = 'qa';
```

- 副本路径 **必须**位于 `/home/ys/codes/XenoDev/out/` 下 —— `CollectionReader._checkout_root`
  取库路径的 `parents[1]` 作原文根,放别处会导致 `raw_ref` 全部解析不到(静默产 `text=''`)
- 原 `collection.db` **只读、零改动**
- **本绕法使范围更可审计**:整个提取范围由**一条 SQL** 定义,可复现、可核对

⚠ **副作用与已接受**:census 仍会为 qa 这个 form 走一遍空池(`picked=[]`),verdict 里 qa 相关
读数恒为 0。**这不代表「qa 无信号」**,只代表本批未纳入。

### 3.2 排除 qa,及理由(实测后更新 · 理由变了但结论更强)

**qa 不纳入本批。**

⚠ **起草时的理由是错的**:原以为 qa 便宜(文本短 · 均 178 字符)。**计时试验推翻了这个假设** ——
每次 API 调用有约 **8 秒固定开销,与输入长度基本无关**。qa 的代价是
**6000 次调用 × 8 秒 ≈ 13.3 小时**,换约 187 条信号。

**不是 token 贵,是调用次数贵。** 排除 qa 的结论不变,理由更硬。

⚠ **这是效率取舍,不是「qa 没有信号」的结论。** 如果日后要纳入 qa,**必须作为独立的新批次
重新预注册**,不得中途追加进本批(中途追加 = 变相的 optional stopping)。

### 3.3 与既有 41 条的关系

`select_source_ids` 是**确定性**的(按 `sha256(seed_key + source_id)` 排序取前 n),所以把 n 从 40
扩到全池时,**原来那 40 条仍在新集合的前 40 位** ⇒ **现有 41 条信号是新批次的子集,不丢弃、不重跑冲突**。

⚠ 已知且已接受:这 41 条的**机器答案**已泄漏约 19 条(见 PRD 块 (p))。**对本检验无影响** ——
本检验的裁判是市场收益,而**任何收益数字从未被计算过**。泄漏的是「机器认为这是哪只票」,
不是「这只票后来涨没涨」。

### 3.4 ⚠ 治理说明:这是在改一个已冻结的常量

`_N_PER_STRATUM = 40` 的源码注释写着「冻结候选 · census 消费此方案 · **不临时缩**」。本文是在**扩**它,
必须说清为什么这不是「移动球门」(PRD §4-E1 (f) 判据):

| (f) 判据 | 本次是否触发 |
|---|---|
| 看数后**下调**既有阈值数字 = 移动球门(禁) | ❌ 不触发 —— 是**上调**样本量,且**没有任何阈值被改动**(密度阈值 30/stratum、`caliber_version`、`caliber_hash` 全部不动) |
| 目的是让某个**已有的**门槛通过 | ❌ 不触发 —— 密度关早已按 advisory 语义**终裁完毕**(US go),扩样**不重开该结论** |

**判定:不构成移动球门。** 但本条必须写进 trial ledger,由后来者复核。

## 4. 冻结项 B · 检验规格(E2 真被授权时按此执行,不得临场改)

> ⚠ 本节的具体选择**需要 operator 拍板**(见 §7 待决项)。下列是建议值,签署时逐条确认。

### 4.1 数据集切分(利用已冻结的 OOS 窗)

| 集合 | 定义 | 用途 | 可看几次 |
|---|---|---|---|
| **开发集** | §3.1 全部(OOS 窗外) | 调口径、看失败模式、做诊断 | 不限 |
| **确认集** | **OOS 窗 `[2025-12-01, 2026-02-01)` 内的 article + replay**(≈171 条记录 → 约 110 条信号) | **最终检验** | **仅一次** |

**这块确认集是现成的**:C12 从设计之初就把它排除在 census 之外,**至今零次接触**。
它正好解决「定时校准提取器会不会导致过拟合」那个问题 —— **在开发集上随便调,在确认集上只开一枪。**

### 4.2 「命中」的定义

**必须是超额收益,不能是绝对涨跌。** 理由:61% 集中在半导体、78% 是 long —— 用绝对涨跌做判据,
大盘涨的时候几乎全中,测到的是 beta 不是本事。

建议定义:

```
hit = (direction == long  且 excess_return > 0)
   或 (direction == short 且 excess_return < 0)
excess_return = 标的在 horizon 内的收益 − 基准在同窗口的收益
```

**基准(待定 · §7-1)**:候选 SPY / QQQ / 同板块 ETF。⚠ 鉴于半导体集中度,用 SPY 会把
「押对了半导体」记成分析师的本事;用 SMH 则会把它扣光。**这个选择会实质改变结论,必须事前定死。**

### 4.3 Horizon(待定 · §7-2)

`extracted_signals` **没有 horizon 列**(机器该维恒 null,是 D-1 已确认的结构事实),所以 horizon
**必须在本文事前指定**,不能逐条读。

`sampling.py` 已冻结 `_HORIZONS = (5, 20, 60)` 个交易日。

⚠ **三个 horizon 全测 = 三次检验 = 多重比较**。建议:**指定 1 个为主检验**(建议 **20 日**),
另两个标为**探索性**,其结果**不得**单独用于结论、且必须与主检验一同披露。

### 4.4 主检验统计量与相关性处理

- **主检验**:命中率 vs 50%,**单尾 α=0.05**
- **⚠ 必须做相关性修正** —— §1 已实测出严重的簇结构。指定用 **按 `source_id` 与按日期的
  block bootstrap**(而非把 n 条当独立样本)。**不做这个修正,p 值是假的。**
- **同时报告**(不作为主结论):平均超额收益 + 其 clustered SE、按信号等权的组合收益曲线
- **DSR / PBO**:按 M2 既有实现跑,`trial_count` 取 trial ledger 的真实累计值(见 §5)

### 4.5 停止规则(反 p-hacking)

1. **一次性承诺提取范围**(§3),跑完为止。**不允许**「先跑一部分 → 看结果 → 决定要不要继续」
2. 主检验在确认集上**只跑一次**,结果无论好坏都写进 hand-back
3. 任何在看到结果**之后**对 §4 规格的修改,**一律作废本次检验**,必须换新 `caliber_version` 重来

### 4.6 结果的预先承诺解读

| 结果 | 事先承诺的解读 |
|---|---|
| 主检验显著 | **「这套流程(提取器+分析师)在历史窗上有超额收益」** —— 按 forge v5 两级证据制,这是**开发证据**,**不是** alpha 确证。确证仍须 forward 线 |
| 主检验不显著 | **「n≈900 上测不出超额收益」** —— **不得**改口径重测同一批数据。可以做诊断(哪类信号差),但那属于 ②-a lane,结论不得表述为「其实是有的」 |
| 开发集好、确认集差 | **以确认集为准**。这正是确认集存在的意义 |

## 6. 成本 —— ✅ 已实测(2026-08-12 计时试验)

**试验方式**:真盘副本(`/tmp/pilot-timing.sqlite`)· `--sample-size 10`(每 form)· 真 DeepSeek ·
**真盘 `out/e1-census-20260718.sqlite` 全程零接触**(试验前后 checksum 均 `00e69d77`,41 行,gold 表全 0)。

| 实测项 | 值 |
|---|---|
| census 整跑 | **24 条记录 / 226 秒** · api_failures=0 · parse_failures=0 · **truncation_failures=0** |
| 单条 57,185 字符长 replay | **42.3 秒** |
| 单条 813 字符短 replay | **12.5 秒** |

**🔴 成本结构是反直觉的**:

```
每次调用固定开销 ≈ 8 秒(与输入长度基本无关)
长度的边际成本 ≈ 0.0006 秒/字符(57k 字符只比 813 字符多花 30 秒)
```

⇒ **瓶颈是调用次数,不是 token 量。** 唯一的大杠杆是**并行化**(8 秒里绝大部分是网络等待),
但那是代码改动,**不在本预注册范围**;本批按串行预估。

**外推**:

| 方案 | 记录数 | 墙钟(串行) | 主导项 |
|---|---|---|---|
| article | 1055 | ≈2.3 h | 固定开销 |
| **+ replay** | +309 | **+1.5 h → 3.8 h** | 一半固定、一半长度 |
| + qa | +6000 | +13.3 h → 17 h | **全是固定开销** |

**钱**:article+replay ≈ 5.65M 字符 ≈ 400 万 input token。flash 档位下大概率是**个位数美元**。
⇒ **金钱不是约束,时间是。**

### 6.1 ⚠ 环境层拦路虎(正式跑必带,否则 0.4 秒即崩)

首次尝试直接失败:`ALL_PROXY` / `all_proxy` 是 **socks5** 协议,而 `httpx` 未装 `socksio` 扩展 →
`ImportError`(被 `_sanitize_llm_exc` 脱敏成裸 `ImportError`,**报错信息看不出真因**)。

**绕法(零代码、零装包)**:命令前缀 `env -u ALL_PROXY -u all_proxy` —— 屏蔽 socks 变量后
回落到 `HTTPS_PROXY`(http 协议,httpx 原生支持)。连通性已实测(401 = 通,只是探针 key 无效)。

### 6.2 ⚠ `--extractor-variant` 参数被忽略(设计如此,非 bug)

计时试验传入 `pilot_timing_20260812`,DB 实际写入 `llm_extraction_v2_deepseek-v4-flash`。
查证:这是 **forge v6 条款 (D)** 的设计 —— `variant 身份 = proposer 类型 + prompt 模板版本`
(修 literal/llm 混用导致的 trial 记账缺口)。

⚠ **后果(正式跑必须处理)**:本批与历史 41 条**在 `extractor_variant` 字段上无法区分**。
故本批**写入独立的新 DB 文件**(见 §10),不与 `e1-census-20260718.sqlite` 混库。

### 10.6 输出格式对照实验(JSON vs XML · operator 2026-08-12 提议)

**动机**:operator 提出「有实践显示 XML 格式比 JSON 表现好很多」。
**文献锚**:arXiv **2408.02442**《Let Me Speak Freely?》—— 格式约束损害**推理密集型**任务,
`JSON-mode`(约束解码)是最差档;但对**分类**任务 JSON-mode 常持平或更好;
归因是 **schema 约束本身**而非解析机制(证据:解析失败率近零而性能差距仍在;JSON key 顺序都影响推理质量);
「先自由生成再转格式」≈ 自然语言水平。

⚠ **但不据文献推演下结论**(本仓「推演≠真跑」已七次实证)。设计三臂实测以**分离变量**:
臂 A = JSON + `response_format=json_object`(现状)· 臂 B = JSON 但不约束解码 ·
臂 C = XML 标签 + 不约束解码。3 条记录 × 3 臂 × 4 重复 = **36 次真调用**。

| 臂 | 解析/API 失败 | 不同结果集 / 有效次数 | 均耗时 |
|---|---|---|---|
| **A · JSON + 约束解码**(现状) | **1 / 12** | 1/3 · 1/4 · 4/4 | 21–41 s |
| **B · JSON 不约束** | **3 / 12** | 1/3 · 1/3 · 2/3 | 19–84 s |
| **C · XML 不约束** | **0 / 12** | 1/4 · 2/4 · 4/4 | 29–76 s |

#### 结论

**① XML 的优势在解析健壮性,不在稳定性、也不在质量。**
机制朴素:`json.loads` 是**全有全无**(模型多说一句、包 markdown 围栏、思考内容漏出 → 整条作废);
`<signal>` 标签用正则抓,**周围有杂物不影响**。
⇒ 直接对上病灶:§10.4/§10.5 两次跑失败分别是「坏 JSON」与「返空」,**宽容解析器至少能救下第一次**。
⚠ **样本量小**:0 vs 3(n=12/臂),Fisher 精确 p≈0.22 —— **是提示,不是定论**。

**② 反直觉:臂 B(JSON 不约束)最差。**
⇒ 约束解码对 JSON 是在**帮忙**(逼模型别输出杂物)。故论文的「JSON-mode 最差」**不能直接搬** ——
它比的是**推理质量**,我们卡的是**解析成活率**,两个不同的失效面。

**③ 换格式救不了内容不稳定。** A 与 C 在内容集合上同样不稳(均出现 4/4 全不同)。
本实验同时**证伪了 §10.5 初版的「清晰记录稳定」**(见该节更正块)。

**④ 顺带发现:`_N_MAX = 12` 被顶满。**
三条记录、三个臂,几乎每次都提满 12 条 —— 而 12 正是 `census.py` 的 `_N_MAX` 上限。
一份 **388 字符、纯财报数据、零推荐语**的记录稳定提出 12 条候选。
⇒ 这不是「抽取」,是**顶格提案、把筛选全推给下游 caliber 规则**;
且上限被顶满时**每次挑中哪 12 条会变** ⇒ **内容不稳定可能有相当部分源于此,而非「模型想法变了」**。

#### 建议:不是「换 XML」,是「解析器别全有全无」

XML 的收益是**顺带**得到的宽容解析;同样效果可用**更小的改动**取得
(JSON 侧提取第一个配平 `{...}` 块 + 剥 markdown 围栏再 parse · **不动 prompt 契约、不换 template 版本**)。
且必须诚实:**换格式解决不了内容不稳定,也解决不了模型身份缺失** —— 那两条才是根本。
