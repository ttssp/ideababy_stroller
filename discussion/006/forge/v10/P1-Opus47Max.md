## §1 · 现状摘要(架构设计视角)

**(1) 两簇是同一个绑定缺失的两次投影,但投影面不同。**
簇 A 缺的是 **规则 → 执行** 的绑定:`CLAUDE.md:112` 写下 worktree 规约、SKILL §4.2 写下四轮上限,
但没有任何东西把「写下」和「照做」连起来。簇 B 缺的是 **声明 → 校验** 的绑定:
`workspace.source_repo` 被写进每个包、`worktree/baseline` 被写进 schema、
「只减不增」被写进不变量 3,但 `SOURCE_REPO_FM` 是死变量、check-7 恒 exit 0、
模式类识别从未实装。**两者的共同形状是:一个断言被写下,使其为真的那个东西不存在,
而这个落差不产生任何信号 —— 系统看起来是绿的。** 这是我认为本批只有一个根的理由。

**(2) 本轮最刺眼的事实是自指的:簇 B 的解药就是簇 A 的病。**
`check-7:13` 与 `check-8:23` 都写「本 check 永远 exit 0」,各自 `:16` / `:26` 挂一条
「复发 ≥2 次即升级」;`CLAUDE.md:114` 的 hook block 判据同形。而 KG-B15 的判据
**在第 2 次就达成,达成后仍复发到第 4 次**。⇒ 这不是三个孤立选择,而是**本仓面对
「该不该硬拦」这个问题时的默认动作**:先 warn,附一条「≥N 次再说」。
**这个默认动作本身没有任何后续边** —— 谁计数、在哪个 gate 上被读到、达成后谁执行,
三个问题一个都没有答案。⇒ 从架构上看,`warn` 在本仓不是一个「较弱的门」,
而是**一个没有出口的状态**;它与 v9 干掉的 `absent` 态是同一类东西 ——
`absent` 的毛病是「若缺席要被写下,它自己就会缺席」,`warn` 的毛病是
**「若升级要被人记得,它自己就会被忘记」**。

**(3) 但我必须先怀疑本批的独立性。**
v9 已经给出过一个正面针对这一形状的通用机制(obligation control plane:
不可绕过的 gate **预建** pending / satisfied 绑内容身份 / 到期 fail-closed),
且 v9 自己警告过「KG-B13/B14 可能是本条款的**实例**而非独立议题」。
**那条警告对簇 B 四条同样成立,可能对簇 A 也成立。** 本轮 Phase 0 的实证支持这个怀疑:
gate 一接线,74 天没人碰的回审当场就被逼出来了 —— 不是因为有人更自觉,
是因为**有了边**。若如此,v10 该产的可能**不是新机制,而是接线** ——
而 build 侧四个消费 gate 至今 `consumer_wired: false`,v9 的 [A] 从未落地。
**这是我 P1 阶段最希望被证伪的判断**(K 的回声室条款:请优先证伪)。

## §3 · 我现在最不确定的三件事

**(1) 本批有多少条其实是 v9 verdict 的实例,而不是新议题?**
这直接决定 v10 该产什么:若多数是实例,verdict 应是**接线计划 + 完备性论证**,
而不是又一簇新机制。反过来,如果我把实例误判为新议题,v10 就会重演
「造了第二个控制面、两个都没接线」。我倾向前者,但**我是 v9 那轮的 Opus 侧,
对自己上一轮的机制有明显偏袒动机** —— 这条必须由 Codex 侧独立判。

**(2) 「warn 必须自带到期」这条我想提的一般条款,在本仓可行吗?**
架构上我认为 `warn` 应当是**有到期的临时态**(到期自动升级或自动失效),而不是稳定态。
但 v9 `underweight-8①` + README 局限 3 已指出:**本仓的 `due_gate` 没有自然时钟**
(单 operator、跨仓、批次间隔以周计)。warn 的到期会**撞上同一堵墙**。
若时钟问题无解,我这条一般条款就退化成第四条「≥N 次」判据 —— 正是 K 禁止的那种交差。

**(3) A-1 的「关键性分级」假说是否成立?**
我提出「review gate 对被审模块的关键性无感 ⇒ 低风险面上永远能再找出一条 `[P2]`」,
证据是 T041(自用脚手架,6 轮 15 条)vs FU-R5F4(`gate.py` 真门禁,1 轮 0 条)的对照。
**但这是 n=2 的对照,且我是提出者、未经 producer 确认。** 若假说不成立,
A-1 的修法方向会从「按关键性分级」滑向别处。请勿因它出现在快照 Part 1 就当既成事实 ——
快照 Part 5.1 已标它为假说。
