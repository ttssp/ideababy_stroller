## 1 · 整合摘要

**本轮最重要的事件是我的地基被证伪了一半,而且是我自己请求的。** 我 P1 §1 写「四条机制侧全都
写对了,失效整齐落在执行面」,并请 Codex 优先证伪。Codex P2 用 SOTA 做到了:in-toto 的 owner
**先签必经步骤**、GitHub 的 requirement **由 branch/ruleset 预置**、SLSA 的 subject digest
**先绑内容再验后生证据** —— 成熟体系全都**在证据之外先定义 obligation**。⇒ 本仓不只是「造了门
没人调」,而是**从未有 obligation 层这个设计**。`execution gap` 与 `design gap` **并存**。
我接受这条推翻,并认为它必须写进 verdict 的理由链:**若只说「加个机制」而不说清原诊断错在哪,
下一次仍会先去改 SKILL 措辞** —— 那正是 K 第 1 条点名的「第三条建议」。

**「缺席」的处置,SOTA 给了现成解且不误拒老包。** GitHub required check 必须取得
`successful` / `skipped` / `neutral` **状态**才放行,未上报则保持 Pending 并阻断
—— 即「不适用」**必须被主动申报成 skipped,不能靠沉默**。这一条同时满足 K 第 3 条
(不是「未带就拒」,老包申报 skip 即合法通过)和 K 第 1 条(是机器判据,不是又一条建议)。
Gerrit 的 `copyCondition` 进一步说明:全量撤销会因 merge-base 漂移误报,**细分可减误报但需可信分类**
—— 这是我们设计失效边时必须吸收的误报边界。

**但 SOTA 同时给了三条限缩,本轮不得越过。** ① **OPA 明确只是 decision point**,
enforcement 接线必须由应用/CI 主动做 ⇒「采 policy-as-code 即解决」被反证,**逐入口接线的成本
不可省**(这与 Codex P1「通用机制无法自动发现任意未调用步骤」同向,现在有 SOTA 撑);
② **SLSA 能证明「谁对哪份内容作何声明」,但不能证明 review 足够**,且 producer 与证据**同信任域**
⇒ 可信 control plane 须另立;③ **WORM / Merkle 只保证「已有记录不可改」,不生成 obligation**
⇒ immutable 化解决不了「该产却未产」。合起来:**本轮 verdict 不得承诺「采个标准 / 加一条通用条款」
就根治**,必须把「枚举完备性」写成已知敞口。

**XD-44 第一次有了真实实证(全部来自 Codex 侧单侧检索,我方 `WebSearch` 后端 400 故障,
第二次复发)**:19,177 reviews 的规模/新增行与 review changes 相关;另一研究里 70% 约 1–2 轮
但**精确轮次预测很差**;defect escape 与 review coverage / 参与度 / 专家度显著相关,
**但 100% coverage 仍有缺陷**;**未取到任何支持统一停轮阈值的研究**。⇒ 分档有实证支撑,
「finding 类别重复作收敛信号」**没有**。
