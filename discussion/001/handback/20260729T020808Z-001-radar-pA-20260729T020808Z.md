### 2.5 评审(**独立子代理 · 非 codex** · 4 轮 · 22 findings 全修)

这是连续第 5 个走替代路径的 task(T021 / FU-KG29 / FU-KG30 / T022 / 本批)。

两条最重的都是「**写得进、读不回**」类,且都在 **O5 后验那一刻**才会暴露:

1. **U+2028 / U+2029 / U+0085**:`json.dumps(ensure_ascii=False)` 不转义它们,而
   `str.splitlines()` 在它们上断行 → 一条记录被读成两半。后果不是「少读一条」——
   fail-closed 是**文件粒度**的,**同文件里健康的行会被一起拖下水**,且报出的行号指向一条
   `json.loads` 能正常解析的行(诊断跟着失真)。快照是 LLM 渲染文本,这是现实输入。
2. **截断在多字节字符中间**(崩溃 / kill / ENOSPC):`UnicodeDecodeError` 是 `ValueError`
   子类,既不是 `JournalCorruptError` 也不是 `OSError` → **整整一类损坏绕过 fail-closed 契约**,
   operator 只看到字节偏移 + 调用栈。本项目结论/理由/快照全是中文(一字 3 字节),
   **不需要手工编辑就能触发**。

另修:`--journal` 在子命令前被 argparse 子解析器的 default **静默盖掉**(exit 0、打印「已留档」、
档落在缺省文件);`date.fromisoformat` 在 Py3.11+ 顺带收 `20260729` / `2026-W31-1` 并原样落盘;
0 字节 / 纯空白快照被接受;目录 / FIFO / 字符设备 / 无权限的诊断在说谎或裸奔 traceback。

## §4 方法论教训

1. **「测试绿了」和「测试测到了」是两回事,覆盖率是那把尺。** P2-A 的回归测一度绿得不是
   地方:`raw[:-3]` 砍的是行尾 ` false}\n`(全 ASCII),文件仍是合法 UTF-8,走的是既有的
   JSON 解析分支;而断言写的是「`行` in err」,那条既有消息里恰好也有「行」字 ——
   **测试用错误的代码路径产出了一个正确的事实**。揭发它的不是人眼,是覆盖率(99%→95%,
   少掉的正是修复本体两行)。
2. **断言「诊断存在」不等于断言「诊断正确」。** 修完上一条后,`lineno = 999999` 这个 mutation
   **仍然存活**,因为我只断言了「有个『行』字」。行号**就是**这段修复的全部价值 ——
   只断言它存在等于没断言。这条比第 1 条更尖:它溜过了一个**专门为抓第 1 条而写**的测试。
3. **修一半比不修更危险,因为它看起来像修完了。** `--journal` 的 argparse 修复首轮只改了
   `record` 漏了 `list` —— 被新加的回归测当场抓到。
4. **文档声称的完备性必须和代码对得上。** `_read_snapshot` 的 docstring 声称「三类坏输入各给
   可执行诊断」,而权限那第四类在裸奔 traceback;stat 层还在 try 之外。**六个月后没人会重读
   代码去核对那句话**。
5. **测试不该有能力碰生产落点,哪怕是在它失败的时候。** P1-1 的回归测在**红**的时候会往仓里
   cwd 相对的缺省 journal 写一条假档(真发生了一次,已清)。
