# Hand-back · 001-radar-pA · T031

## §1 Rationale(执行摘要)

T031 taste 反馈标记留存 + 读回(O6 · v0.1 只留存不闭环)

## §2 触发原因 + 决议链

**tag=feature**:T031 按 IDS `/handback-review 001` 授权起跑并 ship。

### 2.1 交付了什么

`JsonlTasteStore` 实装 T001 `TasteStore` —— operator 对每条 judgment 标「符合 / 不符合我的
taste」,append-only 持久化 + 可读回,加 `python -m radar.taste.cli {mark,list}`。
**v0.1 只留存 + 读回,不做闭环自动调参**(R1-3 · 那是 v0.2 · 在此实装即越界)。

### 2.2 刻意不发明 spec 没定义的语义

- `TasteMark` 是 frozen domain(只有 `judgment_claim` + `aligned`)⇒ **身份只能是 claim 字符串**;
- 同 claim 多标 = 多行并存,**无 latest-wins** —— 人读面把歧义**印出来**让 operator 自己判,
  替他挑就是发明 spec 没定义的语义(照 OQ-A1-1 的纪律);
- 极性必须**显式**给:两极是对称的,给任一极当默认会让「忘了标」静默变成「标了那一极」,
  那是往 taste 库里灌噪声,而 O6 的全部价值就是这个库的真实性。

### 2.3 评审(**独立子代理 · 非 codex** · 4 轮 · 19 findings 全修 · 末轮 **approve**)

⚠ **provenance 显式声明**:**不是 codex**,**未产生也未冒充 codex verdict**。配额墙至 2026-08-02。

**最有价值的一条是方法论层面的 —— 建议回流 forge**:

人读面的消毒最初写成**六项 denylist**(`\n` `\r` U+2028 U+2029 U+0085 ...),而那张表是从
**存储层**那个 bug 推出来的(json.dumps 不转义 ∩ splitlines 会断行)。可它要防的是
**终端渲染**被伪造 —— 两个集合**几乎不相交**。评审用真 VT 模拟器实测:

- 那三个 Unicode 分隔符**终端根本不断行**(等于白中和);
- 真能骗人的 **VT / FF / ESC / BS / DEL / RLO / ZWSP / BOM 一个都没拦**;
- 其中 **ANSI 光标上移 + 清行比换行注入更坏** —— 换行只是**多印**假行,ANSI 能**擦掉真行**:
  实测把 CLI 自己印的表头改写成「taste 标记: (empty) 0 tiao」。

而本仓**早就为同一威胁类退役过 denylist**:`reconstruct/reconstructor.py` 的
`_serialize_untrusted_field` docstring 明写「R5 denylist 打地鼠 → R7 allowlist(拒整个补集)」,
R8 还因白名单宽了一类吃过 codex high。**重蹈 R5 没有道理。**

现改判据为 **Unicode 类别**(Cc/Cf/Cs/Zl/Zp + noncharacter),**复用** `evidence/anchors.py`
既有类别表(不在本层重造 · KG-29),本层只加 Zl/Zp 并说明为什么(那张表是给**标识符合法性**
用的,本层管**渲染面**,正确集合不同)。正文(汉字 / ASCII / 符号 / 变音符 / emoji)一个字不动;
转义分隔符自身保证映射**单射**(评审穷举 11110 个串 · **0 碰撞**)。

### 2.4 与 T030 完全同族的一条 P1

U+2028/2029/0085 被 `splitlines()` 断行 → 整个 taste 库读不回来。**与 T030 的 P1 同族**:
两个并行 task 各写一遍 jsonl 读回,同一个坑各踩一次,且**连修复也漂**
(本 task 早一轮补了 `UnicodeDecodeError` 包装,T030 当时没有)。详见 T030 hand-back §3.4。

### 2.5 已知取舍(**写成断言**,免得下次被当 bug「修」掉)

1. **ZWJ(U+200D)属 `Cf`,会被中和** ⇒ ZWJ emoji 序列显示会拆开。有意为之。
   评审给了比「emoji 在本领域少见」更硬的理由:**消毒只在显示层** ——
   store 读回**逐字节**相等、`--json` 保留原文,operator 永远能取回原文。
   这才是「中和一个语义有效的格式字符」可接受的真正依据(ZWJ 在天城文 / 阿拉伯连写里承重)。
2. **终端折行**仍可把 claim 文字推到物理行首(评审在 40 列下实证)。**任何码点规则都关不掉**,
   要宽度感知截断。它擦不掉真输出,表头与汇总都在,`--json` 仍权威 ⇒ 弱于已修的那些。

## §4 方法论教训

1. **守卫的测试可以在守卫被完全关掉的情况下通过 —— 而且在同一个 task 里连发三次。**
   round-1 P2-1(只断言表头)/ round-2 P3-1(截断码点表)/ round-3 P2(比较两条**不同** claim
   渲染出的两行,而它们本来就带不同行号与极性标签)。**每一次都落在最新加的那道守卫上。**
   最后一次的判据是:把 `_one_line` 换成恒等函数 → 16 条测试红,而那条**专门测它**的测试
   **照样绿**。修法是**把脚手架固定住**,只比被渲染的那一段。
2. **消毒判据要从「威胁在哪一层」推,不能从「上一个 bug 长什么样」推。** 见 §2.3。
3. **误伤正文的消毒和漏网的消毒一样会失效** —— 前者会被人关掉。故「不动正文」这一侧也钉了
   反向 mutation(把 Mn/So 也中和 → 2 failed),两头都锁。
4. **lint 是承重的,不是装饰。** 我误跑了两次补丁脚本,提交里带了一个**重复的测试函数定义** ——
   ruff 的 F811 抓到(重复定义会让**前一个静默失效**,正是本 task 反复付账的那一类)。
