## §1 Rationale(执行摘要)

FU-KG30 SHIPPED —— 修真跑才可能暴露的两个 provider 行为缺陷:①真 DeepSeek 把 JSON 包在 markdown 围栏里返回,而 graph/builder 与 judge 都是裸 json.loads,全链第 2 环 hard-fail;②图 JSON 撞 max_tokens=2000 被拦腰截断且**随机**(同 prompt 一次 4729 字符完整、一次 6462 字符被截),而客户端丢弃了 provider 给的 finish_reason,使「被截断」与「返回垃圾」无法区分。修法按 operator 裁定收成**一处共享 helper**(radar/llm/json_response.py),builder 与 judge 各调一次,直接规避 KG-29 那类同一谓词多处漂移。容错边界严格:只容围栏,绝不从任意文本捞取(注入面)。真 provider 冒烟两个消费端均通过。⚠ 评审来源为**独立子代理 x2,非 codex**(配额墙至 2026-08-02),7 条 finding 全部实测复现后修,其中两条最严重的由两名评审各自独立命中。⚠ 框架级那半已记 dogfood KG-30(ship 门不含真 provider 冒烟 → 四个 task 全绿 ship 却在第一次真跑第一环炸),回 IDS forge,不当场改。

## §2 触发原因 + 决议链(按 frontmatter `tags` 逐条说明)

### tag `drift` — 替身的输出形态与真 provider 的实际行为长期脱节

**决议链**:T022(PPV P2 owner)开发完成 → operator 2026-07-28 授权**第一次全链真跑**(真 OpenAlex +
真 DeepSeek)→ 链条在**第 2 环**崩 → 诊断探针定位根因 → 因越 T022 file_domain,按「不当场改」escalate
→ operator 裁定**起本 FU 先修** + **修法收成一处共享 helper** → 本次修完。

**缺陷 ①(真跑实证)**:真 provider 不遵守「只输出严格 JSON(无解释文字)」这条 prompt 指令。

```
ValueError: LLM 图响应非合法 JSON(坏-JSON · 008 KG-24/25): Expecting value: line 1 column 1 (char 0)
  at graph/builder.py:158        ← 全链第 2 环 · 壁钟 22 秒

诊断探针拿到的真实响应:
'```json\n{\n  "nodes": [\n    {\n      "node_id": "m1", ... }\n  ],\n  "edges": []\n}\n```'
```

**缺陷 ②(修完 ① 后冒烟仍炸,同一类根因)**:图 JSON 撞 `max_tokens=2000` 被拦腰截断。

```
长度=6462  ``` 出现次数=1        ← 只有开头围栏,没有结尾
尾部='..."source_ref": "https://doi.org/10.1016/j.engappai.'   ← JSON 断在半路
另一次同 prompt:finish_reason='stop' · 4729 字符 · 完整
```

**随机性是最难查的部分**:图的大小随 LLM 波动,一次装得下、一次装不下 —— 表现为**间歇性**「坏 JSON」。
更糟的是客户端**丢弃了** provider 给的 `finish_reason`:provider 明明已经告诉我们「这是被截断的」,
而我们把这条信息扔了,于是「被截断」与「返回垃圾」在下游长得一模一样。

**为什么这不是普通 bug —— 它活了多久**:T011 / T012 / T020 / T021 四个 task 全部走完完整 ship 流程
(TDD red-green 有证、评审过、§4.4 verifier 过、730 测全绿),而「LLM → JSON 消费者」这条边**一次也没
对真 provider 验过** —— 所有替身都返回**裸 JSON**,即测试作者想象的形态。spec §7 的 PPV 明写「反 PPV
红线:全链任一环 mock = 不算 PPV」,但 PPV 只是**声明**,没有任何 task 的 ship 门要求真调一次。
真相拖到 PPV owner task 才浮出,**晚了 4 个 task**。→ 已记 dogfood **KG-30**(见 §3C)。

### tag `spec-gap-fix` — 修法与边界(operator 两项裁定已落地)

**裁定一:处置路径 = 起 FU 先修,不扩 T022 的 file_domain**(边界干净,修复有自己的证据链)。
**裁定二:修法 = 一处共享 helper,builder 与 judge 各调一次**(直接规避 KG-29 那类「同一语义谓词
多消费端各自实装、无 SSOT 也无漂移检测」)。

新增 `radar/llm/json_response.py::parse_llm_json(raw, *, context)`,放 `radar.llm` 因为这是
**provider 行为**的容错(不是图/判断的领域逻辑);**不改** `DeepSeekLlmClient.complete` 的契约
(它仍返 provider 原文,散文消费者不受连带影响 —— operator 已否掉「在客户端里剥」这条路)。

**容错边界刻意严格:只容围栏,绝不模糊捞取**。理由不是洁癖,是**注入面**:上游 prompt 里封着不可信的
论文 title/abstract,LLM 可能复述其中被注入的素材。若实现成「捞第一个 `{...}`」,响应里**任何**一段
伪造 JSON 都可能被当成结果 —— 而图与判断正是证据链的源头。故围栏外出现任何非空白文本 → raise;
两个围栏块 = 歧义 → fail-closed 不猜。

**越域说明**:第二格(截断)改的是 `llm/deepseek_client.py` = **T005 域**。经 operator 2026-07-28
显式授权并进本 FU(同一类根因,且正是本 FU 自己的冒烟判据逼出来的),`file_domain` 已补,如实标注。

### 评审(⚠ 来源 ≠ codex · 两名独立子代理)

`risk_level: high` → §3 要求 path A 强制。codex 仍在账号级配额墙内(重置 **2026-08-02**),
operator 2026-07-28 明确指定走**独立子代理评审**。实跑 2 个(红队对抗视角 + 正确性/回归视角),
均判 needs-attention。**7 条采纳,全部我自己实测复现后才修**:

- **[两名评审各自独立命中 · high]** 截断检查排在 content 校验**之后** → 「预算在出可见 token 前就
  耗尽」这个**最严重**的截断场景,反而拿到**最没信息量**的报错「content 空/非文本」——
  恰好退回本 FU 要根治的那种误导。实测复现(`content=''` / `'  \n'` + `finish_reason='length'`
  均报错方向反了)。真实触发路径:`RADAR_LLM_MODEL` 可切 deepseek-reasoner,CoT 耗尽预算时正是此组合。
- **[两名评审各自独立命中 · medium]** 我的注释宣称「两个围栏块整体不匹配(歧义 fail-closed)」——
  **实测是匹配的**:两块被回溯拼成一个 payload,最终 raise 只因拼接结果恰好不是合法 JSON。
  那是**碰巧**,不是设计:换成 `strict=False` 或 json5 就静默失守,而注释还说正则挡住了。
  已改为由正则自己拒(负向前瞻禁止「独占一行的围栏」),**不误伤**字符串行内的 ``` 字面。
- **[medium]** 上限调 4 倍而 30s 超时没动 → 失败面只是从「坏 JSON」平移成「超时」,且发生在
  token **已生成已计费之后**、文案完全不指向 max_tokens —— 与本 FU 存在的理由同构。已改 180s。
- **[medium]** `max_tokens` 的**生效路径**无测(mutation:删掉请求体里的该字段,全量测照样绿)——
  断言常量值 ≠ 断言它生效。已补测。
- **[medium]** builder 的「顶层非 JSON 对象」守卫无测(judge 侧有对称测)—— 删掉后
  `TypeError: argument of type 'int' is not iterable` 会裸奔到调用方。已补对称测。
- **[low]** 「8000 = deepseek-chat 输出上限」**没有出处**:真实上限是 **8192**,8000 是其下的保守值。
  这正是本仓记过的反复失败模式「没有出处的数值边界别写」。已改成标明真实上限 + 取值理由。
- **[low]** `except (JSONDecodeError, TypeError)` 里的 `TypeError` 是死分支(isinstance 守卫在前)。
  按「冗余代码 → 删码」删掉,不留看似承重实则不通电的防线。

### D. 本轮方法论教训(建议与前两批一并回流)

1. **诊断文案的盲区本身就是缺陷。** 我的错误文案只印响应**开头** 200 字符,而截断的证据全在**尾部** ——
   看到的是一个长得完全正常的 ```json 开头,**白烧了一次真调用**才定位。已改成首尾都印,并有测钉住。
2. **「宣称 ≠ 实做」这次栽在我自己的注释上。** 我写「两块围栏整体不匹配」,评审一跑就打脸:
   实际匹配,fail-closed 是下游 `json.loads` **碰巧**兜住的。**安全性质不该靠别的模块的实现细节承重。**
3. **验证工具自身会失牙(第二次)。** mutation 把 `_MAX_TOKENS = 8000 → 2000` 是**等长**替换,
   同一秒内改回时 CPython 的 `.pyc` 缓存(按 mtime **秒** + size 判定)不失效 → 跑的是陈旧字节码,
   baseline 假红。**等长 mutation + 秒级 mtime = 静默失效**,已加 `PYTHONDONTWRITEBYTECODE=1`。
   (上一批的那次是 `"1 xfailed"` 含子串 `"failed"`。同一族:验证工具没有自己的验证。)
4. **改一个旋钮必须看它的配对旋钮。** 上限与超时是一对 —— 我差点只改一半,那样只是把失败面从
   「坏 JSON」平移到「超时」,而且移到了**更贵**(token 已计费)且**更难认**(文案不指向根因)的位置。
5. **mutation 存活的两种成因,处置相反**(本轮再次应验):空响应守卫存活 → 查明是**代码冗余**
   (上游客户端已覆盖、下游 json.loads 同样抛)→ **删码**;而 `max_tokens` 生效路径存活 → 是
   **测选错断言对象**(断了常量值而非它进请求体)→ **补牙**。
