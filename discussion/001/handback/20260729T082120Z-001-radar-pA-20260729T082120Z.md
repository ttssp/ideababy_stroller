### 2.2 为什么「一处调用」不成立

`JournalEntry` 六字段(`src/radar/domain/__init__.py:287-296`),按「evaluate 手上有没有」分:

| 字段 | evaluate 能否机器填 | 依据 |
|---|---|---|
| `direction_name` | ✅ | 入参 |
| `date` | ✅ | 系统时钟 |
| `briefing_snapshot` | ✅ | 渲染好的文本已在 `cli/evaluate.py:139` 手里 |
| `conclusion` | ❌ | 见 (a) |
| `rationale` | ❌ | 见 (c) |
| `decision_delta` | ❌ | 见 (b) |

**三填三不填 ⇒ evaluate 构造不出这个对象**。「一处调用」在定义上就不成立;不是「多写几行」,
是那三个值**不在机器的信息集里**。三个各有独立成因,不能一起解决:

**(a) `conclusion` —— 不是词表映射问题,是聚合问题。**
⚠ 我上一版口头描述的「四环对三值没有干净映射」**方向对但描述不准**,在此更正:
`RadarRing`(投入/试点/观察/暂缓)挂在 **`Judgment.radar_ring`**(`domain:259`)——
**每份 briefing N 条判断各带一个**;`JournalEntry.conclusion`(投/观望/不投 · `domain:289`)
是**整次评估一条**。**两者层级不同**,词表差异只是这件事的表征。
spec §1-O5(`spec.md:92`)只说「每次评估结论(投/观望/不投 + 日期 + 理由 + briefing 快照)
可**留档** journal」,**从未定义 N 条 judgment 如何聚合成 1 个评估结论**(取众数?取最高环?
按证据数加权?)。机器要填就得自己发明一条 spec 没有的聚合规则 —— 那正是 OQ-A1-1
立的纪律所禁止的(「不在 XenoDev 当场定语义」)。

**(b) `decision_delta` —— spec 自己写死它是 operator 事实,机器原理上不可观测。**
spec §6 O7 验收行(`spec.md:267`)逐字:「journal 中 **≥1 行标 `decision_delta=true`**
(该次评估**实际改变 operator 投/观望/不投**)」。「operator 的投入决策有没有改变」
发生在人的决策里,**不在任何产物上**;evaluate 没有任何输入能观测它。
这条不是「难推导」,是**类型不对**。而 O7 被 spec 标为「**最强产品成功信号**」(`spec.md:94`),
所以这不是个可以糊过去的边角字段。

**(c) `rationale` —— 是 operator 的理由,不是 briefing 的正文。**
briefing 全文已经在 `briefing_snapshot` 里。把它再塞一遍进 `rationale`,两字段冗余,
且 `rationale` 失去它在 O5「三个月后回看当时判断对不对」里的作用。

### 2.3 于是 spec §7-P2 存在一处真歧义

同一行(`spec.md:277`)的两列互相拉扯:

- **产物**列要求:「briefing markdown 真文件 …… **+ journal 真行**(结论/日期/理由/快照 +
  decision_delta · 可 `SELECT`/读回)」;
- **验证命令**列是:`cd projects/001-radar-pA && <cli> evaluate --direction "<方向>" &&
  ls out/briefing/*.md && <cli> journal list` —— **没有 `journal record` 这一步**。

两种读法都自洽,且**导致完全相反的 XenoDev 工作量**:

- **读法 A(evaluate 自动写 journal 行)**:命令链没 record 是因为不需要 record。
  但那三个字段从哪来?spec 没定义 ⇒ 要么 IDS 补三条定义,要么把三个字段降级/改型 =
  **改 frozen domain + 改 P2 契约**。工作量:一个 FU + 一次显式 domain 授权。
- **读法 B(operator 读完 briefing 自己 `record`,`journal list` 只是验收读回)**:
  命令链没 record 是因为它是**人的动作**,不是自动链的一环。工作量:**零代码** ——
  `python -m radar.journal.cli record` T030 已交付可用;P2 缺的只是**一次被授权的真跑 +
  一次 operator 真决策**。

**我倾向 B**,三条理由:(i) `decision_delta` 的 spec 定义只有人能填(2.2b);
(ii) O5 的措辞是「**可**留档」不是「自动留档」;(iii) T030 task doc `line 45` 把 journal 定为
「C9 run-ephemeral 的例外(**评估结论留档** · 非原料库)」——「结论」读起来是人的,不是机器的输出。

⚠ **但这是我的读法,不是判定**。spec 的**字面**允许 A,而 A 要动 frozen domain,
**超出任何现有授权**。归属该由 IDS 裁,不由建方选一个自己顺手的。

## §4 方法论教训

1. **评审看的是 diff,而最贵的错误可能不在 diff 里。**
   T030 走了 4 轮独立子代理评审、22 个 finding 全修,没有任何一轮碰到 §3 的建议 ——
   因为评审的对象是**代码改动**,而「给 IDS 的下一步建议」是**散文**,不在 diff 里,
   也没有测试能红。它却是这份 hand-back 里**唯一会让 IDS 花钱的部分**。
   ⇒ hand-back §3 的每一条建议,应当和代码一样被要求**给出可复核的依据行号**。
   本包的每一条论断都标了 `file:line`,就是按这条自我要求写的。

2. **「一处调用」这种量级估计,本身就是需要证据的断言。**
   我写下它时,凭的是「journal 的 save 只有一个入口」这个**真**事实,
   却没问「**调用方拿得出参数吗**」。规模估计错得离谱时,通常不是算错了行数,
   是**把一个信息缺口误认成一个编码任务**。
   ⇒ 估「接线」工作量前,先把被接的那个类型的**每个必填字段**逐个问一遍
   「调用方手上有没有」。六个字段,三个没有 —— 这个检查**一分钟**就能做完,
   而它推翻了整条建议。

3. **两列之间的歧义,单看任一列都发现不了。**
   §7-P2 的「产物」列和「验证命令」列各自都完全读得通,连起来才矛盾。
   ⇒ 验收行的自查姿势不是「逐列读」,而是**逐产物追问「谁产生它、在链条的哪一步」**。
   本条正是这么被抓到的。

4. **撤回要撤得比原文醒目。** 原建议已经投递进 IDS,IDS 可能已据此排期。
   所以本包**单独成包**(而不是等下一份 hand-back 里带一句更正)、
   **逐字引用被撤回的句子**、并**明写哪半句撤、哪半句保留**。
   一条被安静更正的错误建议,和没更正没有区别。
